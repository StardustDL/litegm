# v4.3 audio preview in the admin UI + host-derived signed download URLs

## Motivation

Testing audio generation locally surfaced two defects:

1. **Audio artifacts were not playable from the task detail page.** The detail
   view rendered every media artifact through `PrintTile`, which used
   `MediaThumb` — for audio that resolves to
   `/admin/api/artifacts/{id}/thumb`, and the backend deliberately answers with
   a neutral "AUDIO" placeholder JPEG because it does not decode audio. The only
   way to hear the result was the lightbox (`ui.tsx`), which does render an
   `<audio>` element. This contradicted `docs/usage.md` §"管理台" which states
   audio plays inline.
2. **Signed download URLs were pinned to the configured `public_base_url`.**
   `ArtifactStore.download_url` always prefixed `server.public_base_url`
   (`http://127.0.0.1:8080` in `config/litegm.yaml`). Running a second local
   instance on another port therefore handed the browser links to a port that
   nothing was listening on, so the lightbox player could not load the file even
   when it did render.

Both are UI/integration defects: the API side was verified healthy (generation,
`/content` download, Range requests, signed links, valid 8.00 s FLAC).

## Changes

- `web/src/TaskDetail.tsx`
  - `PrintTile` renders `<audio controls>` for `kind === "audio"` instead of the
    placeholder thumbnail, with the filename and a "查看详情" link to the
    lightbox.
  - The thumbnail grid in the right-hand panel does the same for audio tiles.
  - The "大图浏览" button reads "播放器视图" when the primary artifact is audio,
    since there is no image to enlarge.
- `src/litegm/storage.py`: `ArtifactStore.download_url` accepts an optional
  `base_url` override; when omitted the previous configured-URL behaviour is
  unchanged (used by the OpenAI-compatible `response_format=url` path).
- `src/litegm/admin.py`: new `_request_base_url(request)` derives the scheme and
  host from the incoming request (`Host` header, `X-Forwarded-Proto` when
  present) and `_task_dict` threads it into `download_url`. The configured
  `public_base_url` is only a fallback for requests that carry no `Host`.
  No port number is hard-coded anywhere in this path.

## Verification

- Live against the real backend on a local no-auth instance (`--port 8081`):
  audio job submitted and completed; `/admin/api/tasks/{id}` returns a
  `signed_url` on the requested host and port, reachable without
  credentials (`200`, `audio/flac`, 397527 bytes) and answering Range requests
  with `206 Partial Content`, which is what `<audio>` seeking needs. The same
  request via `localhost` returns a `localhost` URL, and a request with
  `Host: gm.example.com` + `X-Forwarded-Proto: https` returns an `https://`
  link.
- `pytest -q -m "not integration"`: 81 passed (3 new tests in
  `tests/test_admin_ui_support.py` cover host-derived URLs, forwarded proto and
  the no-Host fallback to `public_base_url`).
- `tsc -p web/tsconfig.json --noEmit` and `npm run build` succeed; the rebuilt
  bundle contains the new audio UI.
- `litegm check --config config/litegm.yaml` reports ok for all aliases,
  including `audio.generate/minimax-music3`.
- `scripts/fix_utf8.py` reports OK for every edited file.

## Known limitations

- The backend still returns a placeholder thumbnail for audio
  (`/admin/api/artifacts/{id}/thumb`); the admin UI no longer relies on it for
  audio, but other surfaces (task list previews, gallery) keep showing the
  placeholder rather than a waveform.
- `public_base_url` remains the source for the OpenAI-compatible
  `response_format=url` links, which are produced outside a request context;
  those still need to match the port the gateway is actually served on.
- Deriving the base from the `Host` header trusts client-supplied input. Behind
  a proxy that is the intended behaviour; the host only affects the link prefix,
  not signature verification.
