# v1.6 — Unified image model and admin visibility for uploaded inputs

Date: 2026-10-23
Status: completed and verified live

## 1. Unified image model (configuration-driven routing)

A single alias can now serve **both** text-to-image and image editing. Routing is
declared in configuration:

```yaml
routing:
  unified_image_models:
    - alias: <your-unified-alias>   # at the time: image-2.1, the Qwen turbo variant
      generate_task: image.generate
      edit_task: image.edit
```

The same alias is defined once under `tasks.image.generate` (no `image_slots`) and
once under `tasks.image.edit` (with `image_slots`). Requests are routed by whether
input images were supplied:

* no images → the generate variant;
* images present → the edit variant.

### Endpoint

`POST /v1/images` — one entry point for both operations:

* JSON body → text-to-image (same body schema as `/v1/images/generations`);
* `multipart/form-data` with `image` files → image editing (same fields as
  `/v1/images/edits`).

Responses are the OpenAI `ImagesResponse` shape either way. Unified aliases are
also accepted on `/v1/images/generations` (no images) and `/v1/images/edits`
(images), and non-unified aliases keep working exactly as before.

### Validation

Config loading rejects a unified alias that is missing from either task, whose
generate variant declares `image_slots`, or whose edit variant lacks them.
`GET /v1/models` lists a unified alias once, with `capabilities.unified = true`,
both tasks, the accepted endpoints and the routing rule. The admin config view
shows the routing table.

### Verification (live backend)

| Request | Result |
|---------|--------|
| `POST /v1/images` JSON, unified alias, 512×512 | 200, 10.0s, 512×512 RGBA |
| `POST /v1/images` multipart, unified alias, 256×256 source | 200, 17.4s, 1024×1024 RGBA |
| `POST /v1/images/edits`, model `qwen-image-2.1-turbo-edit` | 200, 17.8s, 1024×1024 RGBA |

Edit output follows the source image canvas (the edit workflow derives it from the
input), so the source image size determines edit cost — the test source is 256×256.

## 2. Admin UI: uploaded inputs are visible

Task detail now includes every uploaded input image, not just the prompt:

* store: `input_images` gained `mime_type`, `width`, `height` and `role`
  (`target` = the image being edited, `reference` = additional inputs), captured
  at upload time;
* admin API: task detail returns `input_images[]` with metadata and a preview URL
  (`GET /admin/api/tasks/{task_id}/inputs/{index}/raw`, session-gated);
* admin UI: a new "输入图片" section shows thumbnails labelled `编辑目标 image_1` /
  `参考图 image_N` with filename, dimensions and MIME type, and states when a
  request carried no images (text-to-image).

Verified live: an edit task reports `role=target`, `256×256`, `image/png`, and the
raw endpoint returns the bytes (HTTP 200).

### Schema migration

Existing databases are upgraded additively at startup (`PRAGMA table_info` + `ALTER
TABLE ... ADD COLUMN`) instead of requiring a wipe. This was needed because the
running database predates the new columns.

## 3. Verification tooling made cheap

`scripts/verify_aliases.py` no longer regenerates every model by default:

* default set is the essential paths (the unified alias for generate + edit, and
  `qwen-image-2.1-turbo-edit` for the dedicated edit endpoint);
* default generation size is **512×512**, edit source is **256×256**;
* `--aliases a,b,c` selects specific aliases, `--all` restores the full sweep,
  `--size` overrides the output size.

Essential run: 3/3 succeeded in ~45s (previously ~5 minutes for 12 cases).
