# v4.5 deployment notes: `./data` ownership and `.config` template paths

## Motivation

Two failures were hit in sequence on a real Linux deployment after the image
build was fixed (v4.4):

1. `config error: task 'image.generate' model 'z-image': template not found:
   /app/config/workflows/z-image-general.json` — the deployment config referred
   to the model's own template as `config/workflows/...`, which resolves against
   `base_dir` (`/app`) and therefore points at the image's *example* directory.
   Templates kept in the mounted `.config/` must be referenced as
   `.config/workflows/...` (see `docs/usage.md` §2).

2. `sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) unable to open
   database file` at `TaskStore(config.storage_root() / "litegm.db")`, with the
   container restarting (`exited with code 2`). The host's `./data` was owned by
   root, so UID 10001 could not create `litegm.db`. The v4.2 entrypoint only
   repairs ownership when the container starts as root; in this deployment it
   did not take effect. `sudo chown -R 10001:10001 data` resolved it.

Both are operator-side (config and host directory), not code defects, but the
first-deployment guidance was too thin to diagnose them quickly.

## Changes

- `docs/usage.md` §9: new subsection "首次部署：先修正 `./data` 属主" documenting
  the exact SQLite error, why the image-stage `chown` cannot help with a bind
  mount, when the entrypoint repair does not apply, the one-line fix
  (`sudo chown -R 10001:10001 data .config`), and a `docker run` probe that
  reports whether `/app/data` is writable by the runtime user.

## Verification

- The documented command was run on the deployment host and the gateway started
  successfully.
- `fix_utf8.py` reports OK for `docs/usage.md`; `check_doc_links.py` finds no
  broken links.

## Known limitations

- Ownership has to be corrected again if `./data` is ever re-created by root
  (for example after `docker compose down -v` with an empty bind source).
- The template-path rule is still only documented, not enforced; a clearer error
  message suggesting `.config/workflows/...` for missing templates would help
  but is left for a follow-up.
