# v2.1 — Video task families (config-driven routing)

Date: 2026-10-24
Status: completed and verified live

## Scope

Allow callers to use a single **video family name** as `model`; the concrete
variant is selected from the input fields actually supplied. Reference video/audio
inputs remain out of scope (OpenAI's `input_reference` only accepts images).

## Configuration

```yaml
routing:
  video_families:
    - family: minimax-h3
      task: video.generate
      text_to_video: minimax-h3-t2v
      image_to_video: minimax-h3-i2v
      reference_to_video: minimax-h3-r2v
```

Config validation rejects unknown variant aliases and families without variants.

## Routing rules

| Supplied input | Routed variant |
|----------------|----------------|
| none | `text_to_video` |
| `input_reference` / `first_frame` (single image) | `image_to_video` |
| `reference_images[]` (litegm extension) | `reference_to_video` |

Supplying both `input_reference` and `reference_images` is rejected (400) instead
of guessing. A concrete alias can still be passed to force a specific variant.

## Transparency

Responses now separate what was asked for from what ran:

* `model` — the concrete variant that executed;
* `requested_model` — the caller's original `model` value (e.g. `minimax-h3`);
* the task audit record stores `requested_model` and `input_mode`.

`GET /v1/models` lists the family with `capabilities.video_family = true` and its
variant map, alongside the individual aliases.

R2V with a single reference image previously failed validation: dropping the
