# v1.5 — Additional image workflows via configuration only

Date: 2026-10-23
Status: completed (pending the real-generation verification table below)

## Goal

Add the remaining image-generation workflows to the gateway **without touching the
service code** — only `config/litegm.yaml` and workflow templates — to validate that
the configuration layer really is server- and workflow-agnostic, and that multiple
models can be exposed side by side.

## Added model aliases (configuration only)

| Alias | Task | Template | Key wiring |
|-------|------|----------|------------|
| `qwen-image-2.1` | image.generate | `image_qwen_image_2_1_t2i_api.json` | prompt→452, size→456, seed/steps→458 (KSampler), cfg pinned 1.0 |
| `moss-image` | image.generate | `moss_image_text2image_api.json` | prompt→6, negative→94, size→74 (`EmptyFlux2LatentImage`, 16-multiple), seed/steps→3, cfg 3.0 |
| `qwen-image-2.1-edit` | image.edit | `image_qwen_image_2_1_image_edit_api.json` | target→470, references→475 + dynamically created nodes from 476, encoder 474, no batch node |

At the time three more Z-Image-family aliases (`z-image`, `z-image-safe`,
`zib-image`) were added the same way. They are local-only today — they are not part
of the shipped example — but the mechanism is identical: put their templates into
`.config/workflows/` and add alias entries that reference them there.

Per-model constraints were set from each model's real requirements rather than copied
from the Qwen turbo templates: 16-pixel grid for MOSS, and `cfg` pinned per model
(MOSS 3.0, Qwen 2.1 1.0; the Z-Image family used a 64-pixel grid and cfg 1.0).

## One service-side defect found while adding workflows

`PreviewImage` (used by the Z-Image-family `zib-image` template as its output node)
declares `input.hidden` (`prompt`, `extra_pnginfo`) that ComfyUI fills in at execution
time. The pre-submit validator treated `hidden` entries as required inputs and
rejected the workflow. Fixed in `src/litegm/workflow.py` by excluding `hidden` inputs
from the required set. This is a validator correction only; no API or configuration
behavior changed. The fix applies to any template whose output node is
`PreviewImage`.

## Template adjustment

The Z-Image-family `zib-image.json` referenced a stray `LoadImage` node left over from
the UI workflow (its `image` input pointed at a file that is not guaranteed to exist on
every server). Because `LoadImage`'s `image` input is a COMBO that the validator checks
against the server's input listing, the template copy in `config/workflows/` was changed
to `example.png`, which ships with ComfyUI. This node is not on the sampling path
(it feeds neither the sampler nor the output).

### Issue found in the first run and fixed

`qwen-image-2.1-edit` failed on a **single-image** edit: the base edit template
ships a reference `LoadImage` node (475) with a hard-coded filename, and with no
reference image the node was neither wired nor removed, so validation rejected it.

Fix: `image_slots.reference.optional` — when a variant declares the reference slot
optional and no reference images are supplied, the node is dropped from the workflow
(and its encoder link removed). Enabled for `qwen-image-2.1-edit` through
configuration; single-image, one-reference and two-reference edits all validate and
the single-image edit generated successfully. Covered by a unit test.

### Note on "no service code changes"

The workflow adapters themselves needed no changes: every new alias was wired through
`inject` / `static` / `image_slots` in configuration. Two small, workflow-agnostic
capabilities were added to the platform while adding these workflows:

1. Validator: ignore `input.hidden` schema entries (required for `PreviewImage`).
2. Optional image slots: a template may contain a reference node that should be
   omitted for single-image requests.

Both are generic configuration features, not workflow-specific code.

## Conclusion

The gateway adapted to five additional workflows and one additional edit workflow
purely through configuration. The only code change was a validator bug fix (hidden
inputs), not a change in architecture or API surface.
