# v4.2 container start-up: fix ownership of bind-mounted data

## Motivation

Starting the production stack on an ARM64 Linux host failed at start-up:

```
sqlite3.OperationalError: unable to open database file
  ... src/litegm/store.py, TaskStore(config.storage_root() / "litegm.db")
```

`docker inspect` showed the container running as `10001:10001` with the host's
`./data` directory bind-mounted at `/app/data`, while the host
directory was `drwxr-xr-x root root` — it had been created by an earlier
`docker run` (root). A bind mount replaces the image directory, so the
`chown -R 10001:10001 /app` from the build no longer applies and UID 10001
cannot create `litegm.db`. The same failure occurs on any host where
`./data` exists but is not writable by 10001 (including directories created by
Docker when the bind source is missing).

## Changes

- `docker-entrypoint.sh` (new): when the container starts as root it takes
  ownership of `/app/data`, `/app/.pixi-cache` and `/app/config` for UID/GID
  10001 and then `exec`s the command through
  `setpriv --reuid=10001 --regid=10001 --clear-groups`, so the gateway still
  runs unprivileged. When it is not root (for example `user: "10001:10001"` in
  compose) nothing is changed and the command runs directly.
- `Dockerfile`: copies the entrypoint, makes it executable, sets
  `ENTRYPOINT ["docker-entrypoint.sh"]` and leaves `USER 10001:10001` as the
  default so a bare `docker run` still runs unprivileged; the healthcheck and
  `CMD` are unchanged.
- `docker-compose.yml`: documents why the service starts as root and how to
  opt out (`user: "10001:10001"` plus matching host ownership).
- `docs/usage.md` §9: explains the entrypoint behaviour and the manual
  `chown -R 10001:10001 ./data ./config` alternative.

## Verification

- Image rebuilt locally; `docker run` of the image against a host directory
  owned by `root:root` starts successfully (health `healthy`, `/health/live`
  returns 200), `docker exec ... id` reports `uid=10001`, and `litegm.db`
  appears on the host.
- Control runs on the same root-owned directory: `--user 10001:10001` (the old
  behaviour) still fails with `unable to open database file`, while the
  default entrypoint creates the database (`db ok`).
- 78 unit tests pass; `fix_utf8.py` reports OK for the edited files and
  `check_doc_links.py` finds no broken links.
- The remote deployment itself was left to the operator to restart.

## Known limitations

- `chown -R` on `/app/data` runs on every start; for a large artifact store
  this costs a little time but only rewrites entries whose owner is wrong.
- Containers started with `user: "10001:10001"` cannot repair ownership; the
  host directories must already be owned by 10001.
